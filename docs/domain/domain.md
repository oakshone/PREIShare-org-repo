# PREIShare Domain Brief

## Purpose

PREIShare is a listing-based sharing experience. Its core purpose is to let a person or organization describe something available to share, make that listing discoverable to interested people, and move it through a small, auditable lifecycle until it is no longer available.

This brief defines the minimum domain language for an initial listing workflow. The repository is currently a TanStack Start scaffold, so this is a product-domain proposal rather than a description of implemented persistence or API behavior.

## Actors

| Actor | Responsibility |
| --- | --- |
| Visitor | Views published listings and can begin an interest or contact action if the product permits it. |
| Lister | Creates, edits, submits, and withdraws a listing. A lister may be an individual or an organization. |
| Interested party | Reviews a published listing and expresses interest or requests next steps. |
| Reviewer | Checks submitted content for completeness and policy fit before publication. This role may be combined with an administrator initially. |
| Administrator | Manages exceptional cases, access, moderation, and lifecycle corrections. |
| System | Records timestamps, validates required fields, enforces status transitions, and preserves listing history. |

## Business goals

- Make available items, resources, or opportunities easy to describe and discover.
- Give listers a clear path from an incomplete idea to a publishable listing.
- Give interested parties enough trustworthy information to decide whether to follow up.
- Keep listing availability and ownership state unambiguous.
- Provide a small, consistent lifecycle that can support review and future reporting.
- Avoid collecting or exposing more personal information than the workflow requires.

## Listing lifecycle statuses (closed list)

The following is the complete status vocabulary for a listing. New statuses should not be added without revisiting this brief and the transition rules. `status` must always be one of these fixed choices; free-text status values are forbidden.

| Status | Meaning |
| --- | --- |
| `draft` | The lister is preparing the listing; it is not publicly discoverable. |
| `published` | The listing passed review and is publicly discoverable and available for interest. |
| `under_offer` | The listing has an active offer or pending transaction and is not generally available for new interest. |
| `sold` | The transaction or transfer represented by the listing has concluded. |
| `archived` | The listing is retained for records but is no longer part of active workflows. |

Expected ordinary transitions are `draft` -> `published` -> `under_offer` -> `sold` -> `archived`. A lister or administrator may move a listing from `published` to `archived` when it is withdrawn from active use. A status is not a substitute for an audit history.

## Nested data groups

The listing should be treated as one aggregate with the following nested groups. These groups describe domain boundaries, not a required database schema.

- `identity`: stable listing ID, title, property type, owner reference, and lifecycle status.
- `description`: summary, detailed description, and the reason or context for sharing.
- `availability`: when and where the listing is available, including capacity or quantity when relevant.
- `eligibility`: who may request or receive the listing and any stated requirements.
- `contact`: the controlled contact method or handoff channel for the lister.
- `media`: optional images or supporting files, with labels and ownership metadata.
- `review`: submission, review decision, rejection reason, and reviewer timestamps.
- `audit`: creation, update, publication, withdrawal, completion, and archive timestamps.

Optional groups should be omitted when they do not apply; an empty group must not imply that a requirement has been satisfied.

## Core identity fields

Every listing needs these identity fields before it can be considered valid:

| Field | Requirement |
| --- | --- |
| `id` | Stable, unique identifier generated by the system. |
| `title` | Short human-readable title. |
| `propertyType` | Controlled value identifying the property category. |
| `ownerId` | Stable reference to the lister or owning organization. |
| `status` | One value from the closed lifecycle list above. |
| `createdAt` | System-recorded creation timestamp. |
| `updatedAt` | System-recorded last-update timestamp. |

The identity fields must not contain secrets, credentials, or unstructured private notes. `propertyType` must be one of `multifamily`, `office`, `retail`, `industrial`, `mixed_use`, or `land`; it must not be free text.

## Success criteria for a valid listing

A listing is valid for submission when it satisfies every item in this checklist:

1. It has a stable `id`, an `ownerId`, a title, and a `propertyType`.
2. `propertyType` is one of `multifamily`, `office`, `retail`, `industrial`, `mixed_use`, or `land`.
3. `status` is one of `draft`, `published`, `under_offer`, `sold`, or `archived`; free-text status values are rejected.
4. Its description explains what is being shared in plain language.
5. Its availability states where and when the listing applies, or explicitly says that availability is to be arranged.
6. Its eligibility requirements are stated or explicitly marked as unrestricted.
7. `address` is represented as a nested object group, not as flattened listing-level fields.
8. `financials` is represented as a nested object group, not as flattened listing-level fields.
9. `contacts` is represented as a list of contact records.
10. `contacts` contains at least one entry when the status is `published`, `under_offer`, or `sold`.
11. Any required media or supporting information is present and accessible, if the property type requires it.
12. The lister has confirmed that the information is accurate and appropriate to share.
13. The listing is eligible for publication only after all required fields pass validation and any required review is complete.

A listing is valid for publication only after review requirements are satisfied. Publication must not expose private contact details or internal review notes by default.

## Out of scope

- Implementing a database, Supabase client, migrations, or production data writes.
- Defining authentication, authorization policy, identity verification, or payment processing.
- Designing search ranking, recommendations, messaging, notifications, or dispute resolution.
- Defining legal, safety, accessibility, or moderation policy beyond the data needed to record a review decision.
- Adding lifecycle statuses outside the closed list in this brief.
- Treating the current TanStack Start scaffold as evidence that any of these workflows already exist.

## Handoff note

This brief is the starting contract for a future listing feature. Before implementation, product owners should confirm what PREIShare shares, whether review is mandatory, who may view contact details, and what “sold” means for each property type. Engineering should then translate the confirmed fields into route-level types and validation, keeping domain vocabulary separate from persistence details. The current repository has no implemented data layer, migrations, API routes, or tests for this model.
