## Planned dashboard route tree

```text
/dashboard                 → layout route (shell: header + sidebar + outlet)
/dashboard                 → index (investor home: metrics, portfolio summary, activity)
/dashboard/portfolio       → placeholder child (future mock holdings table)
/dashboard/deals           → placeholder child (future mock deals list)
/dashboard/profile         → placeholder child (future mock profile card)
```

These are the only four pages in scope (requirements brief, section 3). There is no separate `/dashboard/activity` page; recent activity lives on Home.

## Layout vs page responsibilities
- **Layout (`dashboard.tsx`)**: persistent navigation regions only (header, sidebar/mobile nav, main outlet) via `AppShell` from `src/components/layout/`. No metric cards or other page content. Rendered once and kept mounted while child pages swap.
- **Index (`dashboard/index.tsx`)**: dashboard home composition (summary widgets with mock values). Uses the parent layout. Renders no header, sidebar, `<main>`, or `h1`.
- **Placeholders**: minimal pages so nav links have real targets, each a `<section>` with an `h2` and a "coming soon" line. Full UI comes in later topics.
- **Current page**: the URL is the single source of truth. The sidebar highlights the active link and the header shows the page title by reading it; no page passes this in.

## Out of scope for this plan
- Component prop designs and styling tokens (next architecture step)
- Auth guards, sign-in, and loader data shape (later sprints; none exist in the starter)
- API routes, server functions, and Supabase queries
- Pages beyond the four above (for example a full activity feed, admin tools, or checkout)

## Success criteria for implementation steps
- Visiting `/dashboard` shows the layout shell and home index content region.
- Child placeholder paths render inside the same layout (not a blank full-page replace of the shell).
- All four sidebar links reach their page, and the active link matches the current URL.
- On a narrow (phone) width, the shell's navigation stacks above the content and stays usable on every child page.
- Every placeholder page has its own clear title and labels any content as mock.
- No unrelated existing routes (`/`, `/about`) were deleted during dashboard work.
- `src/routeTree.gen.ts` changed only through `npm run generate-routes` or the dev server, and `npm run typecheck` and `npm run build` pass.

## Open questions
1. **Two headers on dashboard pages.** `__root.tsx` renders the starter site `Header` (with its own `<header>` and `<nav>`) and `Footer` on every route, so `/dashboard` shows both that header and the dashboard `Header`. AGENTS.md calls for one `<header>`. Should the root header and footer be hidden on `/dashboard/*`, or kept as site-wide chrome?
2. **Starter home copy.** `src/routes/index.tsx` still says dashboard areas "will be added in a later step" and links to `/about` with a plain `<a>` instead of `Link`. Update now, or leave the starter page alone this sprint?
3. **Route file naming.** `docs/dashboard-ia.md` plans flat files (`dashboard.index.tsx`, …) but the repo uses the folder form (`dashboard/index.tsx`). Both give the same URLs; the IA doc should be updated to match.
4. **Placeholder copy.** Should the Portfolio, Deals, and Profile stubs show a "coming soon" note now, or go straight to their mock components (`PortfolioTable`, `DealsList`, `ProfileCard`)?
