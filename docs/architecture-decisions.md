## Decision 1: TanStack Start file-based routing with a dashboard layout route

### Context

The brief asks for four investor areas (Home, Portfolio, Deals, Profile), each
with its own page and a clear title, inside one persistent frame. The project
already uses TanStack Start, where the route tree is generated from files in
`src/routes/`. A flat layout file (`src/routes/dashboard.tsx`) and a folder
layout file (`src/routes/dashboard/route.tsx`) produce the same URLs; having
both would define `/dashboard` twice.

### Decision

- Use the **folder form** under `src/routes/dashboard/`:

  | File | URL | Role |
  | --- | --- | --- |
  | `route.tsx` | `/dashboard` (layout) | Renders `AppShell` around `<Outlet />` |
  | `index.tsx` | `/dashboard` | Home overview |
  | `portfolio.tsx` | `/dashboard/portfolio` | Holdings |
  | `deals.tsx` | `/dashboard/deals` | Open deals |
  | `profile.tsx` | `/dashboard/profile` | Profile |

- **Update (Sprint 4, 2026-10-22):** the layout moved to the flat file `src/routes/dashboard.tsx`, because Sprint 4 requires that file name. The child pages stay in `src/routes/dashboard/`, the URLs are unchanged, and `dashboard/route.tsx` no longer exists (keeping both would define `/dashboard` twice).
- `src/routeTree.gen.ts` is generated by the router plugin and never edited by hand.
- The **URL is the source of truth for "which page am I on"**. The highlighted nav link and the header title both read it, so they can't disagree with the page shown.
- Nav links and page titles live in **one list**, `src/components/layout/navConfig.ts`. Its `to` field is typed from the generated route tree, so a link to a page that doesn't exist fails the type-check.

### Consequences

- **Adding a page is mechanical:** add a file under `src/routes/dashboard/`, then add one entry to `navConfig`. The page appears in the sidebar, the mobile menu, and the header title.
- **Data loading has a natural home:** each page file can own a `loader`. Data that only Home needs goes on `index.tsx`, not on the shared layout, so other pages don't pay for it.
- **Loaders run on both server and browser.** On client-side navigation, a loader runs in the browser. Anything secret must go through a server function (`createServerFn`), not straight into a loader (see Next sprint foundations).
- **The starter `__root.tsx` still wraps every route** with the template's site header and footer. That puts a second header above the dashboard and makes "Skip to content" the 6th keyboard stop (verification A7, open question 1 in the routing plan).

## Decision 2: One AppShell layout owns the frame; pages own only their content

### Context

The brief requires a header, navigation, and main content region on every
dashboard page, readable on phones and desktops. If each page drew its own
frame, they would drift apart and the navigation would be copied four times.

### Decision

- `AppShell` (`src/components/dashboard/AppShell.tsx`) is rendered once, by the layout route. It contains:
  - a skip link
  - `Header`: brand, current page title, and a "Demo investor" placeholder
  - `Sidebar`: desktop only, 1024px and up
  - `MobileNav`: a "Menu" button, below 1024px
  - `<main id="main-content">` for the page
- Pages render only their own content: a section with a screen-reader `h2`, an intro line, and their widgets. **They never render a header or navigation.**
- Sidebar and MobileNav share the same link list and link style. MobileNav keeps its open/closed state in a single `useState`. There's no global state library.
- The widgets are presentational components with typed props: MetricCard, PortfolioSummary, RecentActivity, PortfolioTable, DealsList, ProfileCard. They show what they're given and never fetch data.

### Consequences

- **The frame is the same on every page,** and a change to navigation is made in one place.
- **Swapping in real data later only touches page files.** The page passes real data into the same props, and the components stay as they are.
- **There is exactly one `h1`,** the Header title, which keeps heading structure predictable for screen readers.
- **AppShell only knows about the dashboard.** The starter site chrome in `__root.tsx` is outside its control (see Decision 1, last bullet).

## Decision 3: Mock data boundary

### Context

The brief's out-of-scope list rules out real sign-in, live Supabase/PostgreSQL
data, payments, admin tools, and production hardening. The project rules
(AGENTS.md, `.cursor/rules/preishare.mdc`) also forbid fetching, database
clients, secrets in source, and `VITE_` credentials this sprint. Stakeholders
must still be able to tell, at a glance, that the numbers aren't real.

### Decision

- **Sample data lives in only two places:**
  - each widget's built-in `DEFAULT_MOCK_*` constant, marked `// MOCK`
  - Home's `demoMetrics` in `src/routes/dashboard/index.tsx`
- **Every sample value is labelled on screen:**
  - Names start with "Sample".
  - Each widget has a "Sample …" note, controlled by an `isSampleData` prop that defaults to `true`.
  - Home shows a "Demo shell" banner.
  - The header reads "Not signed in · sample data".
- **Sample figures agree across pages.** Home uses the Portfolio page's three holdings ($265,000 invested, $300,000 current value, 2 active + 1 pending).
- **Each widget keeps an `emptyMessage` prop,** so an empty list shows a "nothing yet" message, never a blank box.
- **The demo member is a placeholder, not a fake session.** `src/lib/user.ts` `getUser()` returns `null`.
- **No invest, checkout, edit, or sign-in controls exist.**

### Consequences

- **Nothing on screen can be mistaken for live data,** and the code has no paths to a database or secrets to leak (verification S1–S5).
- **The boundary is easy to find.** Search for `MOCK` or `isSampleData` to see every place real data will replace samples.
- **Sample totals are written in by hand.** Home's "$300,000" is not calculated from the rows. That's fine while the data is fixed, but next sprint should calculate totals from real rows.
- **The widgets' types are local** (`HoldingSnapshot`, `PortfolioHolding`, `Deal`, and others). Only `PropertyType` is shared from `src/types`. Next sprint has to map database rows onto these types, or move them into `src/types`.

## Decision 4: Responsive and accessibility baseline

### Context

The brief asks that the layout stay usable on narrow screens with no broken
overlap, and that investors can trust it. Tailwind v4 is the styling system
(`src/styles.css` is the global entry for the whole app).

### Decision

- **Three tiers, mobile first,** with breakpoints defined in `src/styles.css` (`@theme`):

  | Tier | Width | Prefix |
  | --- | --- | --- |
  | Mobile | 320px and up | none |
  | Tablet | 768px and up | `md:` |
  | Desktop | 1024px and up | `lg:` |

  Dashboard code doesn't use `sm:` or `xl:`.
- **The sidebar appears only on desktop.** Tablets get the Menu button and the full content width.
- **Shell and grid layout rules live in `src/styles/dashboard.css`,** imported by `src/styles.css` and placed in Tailwind's components layer. Widget-internal layout stays as Tailwind classes.
- **Accessibility baseline:**
  - one `h1`; pages labelled with headings
  - a skip link
  - a visible 3px focus ring
  - nav links at least 44px tall
  - the current page marked by `aria-current` plus a bar, not colour alone
  - a menu button with `aria-expanded` and `aria-controls`, and its panel hidden with the `hidden` attribute
  - reduced-motion and Windows high-contrast rules
- **Content-specific layouts:** the portfolio table becomes stacked cards on phones, and deal-card status badges move to their own line.

### Consequences

- **Verified** at 375, 768, and 1280px: no sideways scroll or clipping on any page. Keyboard navigation works (`docs/responsive-qa-checklist.md`, verification L1–L7, A1–A6).
- **New components should reuse the `dash-` classes** and the three tiers rather than invent new breakpoints.
- **Gaps that remain:**
  - "Skip to content" isn't the first keyboard stop (A7, Fail).
  - Reduced-motion and high-contrast rules haven't been tried with the settings turned on.
  - No screen-reader or real-device testing yet.
  - Very large metric values wrap mid-number.

## Next sprint foundations

These items aren't built. Each one names what it builds on from the decisions
above, a proposed approach, the decisions the team still has to make, and what
"done" looks like. Packages such as `@supabase/supabase-js` aren't in
`package.json` today. Add them deliberately, with team agreement.

### A. Supabase auth

- **Builds on:** Decision 1 (layout route), Decision 2 (Header placeholder), Decision 3 (`getUser()` returns `null`).
- **Approach:**
  - Use Supabase Auth with a server-side session (cookies), read inside server functions.
  - Guard every dashboard page from the `/dashboard` layout route (`route.tsx`), for example with `beforeLoad`: no session means redirect to a sign-in page.
  - Replace `getUser()` and the Header's "Demo investor" placeholder with the signed-in member.
- **Rules to keep:**
  - Never put the service-role key in source or in a `VITE_` variable. Read secrets only inside server handlers (AGENTS.md).
  - Decide explicitly whether the public "anon/publishable" key may be exposed to the browser. Never assume it.
- **Open decisions:**
  - sign-in method (email link, password, or OAuth)
  - where the sign-in page lives (a new route outside `/dashboard`)
  - which roles exist now, given that admin is a future actor
- **Done when:**
  - Signed-out visitors can't open any `/dashboard` page.
  - The header shows the real member.
  - No secret appears in client bundles.

### B. Live portfolio data

- **Builds on:** Decision 2 (presentational widgets with typed props), Decision 3 (MOCK boundary), and the shared types in `src/types` (ADR-001).
- **Approach:**
  - Create PostgreSQL tables in Supabase for holdings, activity, deals, and profiles.
  - Turn on **Row Level Security** so investors can only read their own rows.
  - Read through server functions called from each page's own loader (Home, Portfolio, and so on), not from the shared layout.
  - Map rows onto the widgets' existing prop types.
  - Calculate totals from the rows, for example portfolio value = sum of current values.
  - Pass `isSampleData={false}` only where real data is shown, and keep the `emptyMessage` states for investors with no holdings yet.
- **Open decisions:**
  - Should the widgets' local types move into `src/types`?
  - How are money values stored (integer cents or numeric)?
  - Where do current-value updates come from?
  - Does the `financialSummary` vs `financials` naming question from ADR-001 need settling first?
- **Done when:**
  - All four pages show the signed-in investor's real rows.
  - Every MOCK constant is gone from the page paths.
  - The responsive QA checklist is re-run with real content lengths and large values.

### C. pgvector-powered search

- **Builds on:** Decision 1 (a new route slots in through `navConfig`), live data in B, and the `PropertyType` / `ListingStatus` vocabularies from ADR-001.
- **Approach:**
  - Turn on the `pgvector` extension in Supabase and store an embedding for each deal or listing description.
  - Generate embeddings **on the server** when a deal is created or changed, never in the browser.
  - Search through a server function that runs a similarity query (for example a SQL function called via RPC).
  - Combine similarity with normal filters: published or open status, property type, minimum investment.
  - Add a search box to the Deals page first, rather than a new top-level page. That keeps the brief's "no surprise pages" rule.
- **Open decisions:**
  - which embedding model or provider (its API key is a server-only secret)
  - embedding size
  - which fields to embed (name, description, location)
  - an index type for when the data grows
  - whether search should only cover deals the investor is allowed to see (RLS applies here too)
- **Done when:**
  - A plain-language query ("industrial in the Pacific Northwest under $50k") returns relevant open deals.
  - Results respect status filters and Row Level Security.
  - No API keys reach the browser.

### D. GitHub Actions CI

- **Builds on:** verification B1–B3 (`npm run typecheck`, `npm run build`, and clean `npm ci` all pass today) and the Node ≥ 22.12 requirement.
- **Approach:**
  - Add a workflow in `.github/workflows/` that runs on pull requests and on pushes to `main`: check out, set up Node 22, `npm ci`, `npm run typecheck`, `npm run build`, plus `npm audit --audit-level=high` to flag known-vulnerable packages.
  - Add `"engines": { "node": ">=22.12.0" }` to `package.json` so local, CI, and Vercel agree.
  - Later: add lint and tests once the team picks tools. None exist today (`docs/onboarding/repo-map.md`).
- **Rules to keep:**
  - CI needs no secrets for typecheck and build while the app uses mock data.
  - When it does (for example Supabase integration tests), use GitHub encrypted secrets, never committed values.
  - Per `docs/onboarding/first-contribution-plan.md`, CI workflow changes need a mentor's go-ahead.
- **Open decisions:**
  - Should a failed check block merging to `main` (branch protection)?
  - Which lint and test tools?
  - Should CI also run the responsive checks?
- **Done when:**
  - Every pull request shows a passing typecheck and build before merge.
  - A broken build is caught before Vercel sees it.
  - The audit step flags known-vulnerable packages. It would have flagged the TanStack Start issue that blocked Sprint 3's deploy, assuming the advisory had been published by then.
